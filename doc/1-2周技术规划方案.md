## 1. 技术目标

在保留现有Next.js内容站能力的基础上，把项目从英文博客模板改造成面向中国大陆学生的中文经管研究辅导、论文润色优化与工具站。第1—2周技术工作应确保：

1. 百度优先抓取、理解和索引首页、作者、服务说明、论文润色、六个栏目和内容详情页，Bing、360、搜狗作为补充，Google作为P2监测渠道。
2. 内容编辑可以继续使用Markdown/MDX，不引入不必要的数据库和后台复杂度。
3. 咨询表单安全、最小化收集数据，并能可靠通知站点所有者。
4. 微信和QQ二维码在桌面及移动端合理展示，并能记录展示入口和渠道来源。
5. 自然搜索、内容互动、论文润色需求和咨询转化形成可测量的数据链路。
6. 首页、正文、字体、图片、统计和咨询功能在国内普通宽带、校园网及手机网络中直接可用，不依赖境外网络环境。

## 3. 总体技术架构

```text
浏览器/搜索引擎
  ↓
Next.js App Router
  ├─ 静态营销页：首页、作者、服务说明、论文润色、咨询、隐私
  ├─ 六个栏目聚合页
  ├─ Contentlayer生成的MDX详情页
  ├─ 本地全文搜索索引
  └─ /api/consultation 咨询接口
        ├─ 输入验证
        ├─ 反垃圾与限流
        ├─ 通知渠道
        └─ 最小化线索记录（部署方案确认后）

数据观测
  ├─ 同区域自托管Umami/国内统计：访问、来源、内容互动、咨询事件
  ├─ 百度搜索资源平台：百度自然展现、点击、关键词、索引和抓取
  ├─ Bing Webmaster Tools：补充搜索展现与索引
  └─ 国内CDN/源站日志：性能、安全、爬虫和错误
```

架构原则：内容页尽量静态生成，关键正文必须出现在服务器返回的HTML中；交互仅用于筛选、搜索、二维码弹层和咨询表单。

### 3.1 中国大陆部署与访问方案

推荐正式方案为中国大陆云服务器或静态托管节点配合国内CDN，使百度蜘蛛、校园网和三大运营商移动网络获得稳定访问。域名、服务器和业务模式确定后，按接入商和主管部门要求完成ICP备案；若网站构成经营性互联网信息服务，应在上线收费功能前核实相应许可要求。

如第1—2周暂时使用中国香港或邻近地区节点，应把它视为过渡方案，并以中国大陆实测结果决定是否上线：至少覆盖中国移动、中国联通、中国电信和常见校园网，检查DNS解析、TLS握手、首屏、表单、二维码、视频跳转及爬虫访问。过渡方案不能替代备案与正式部署决策。

关键资源全部使用可在国内直接访问的来源：中文字体本地托管或系统字体栈；图片、脚本、CSS、下载文件和表单接口使用同域或已验证的国内对象存储/CDN；Google Fonts、Google Analytics、reCAPTCHA、YouTube播放器及其他境外资源不得处于首屏或核心功能依赖链路。

## 5. 内容模型方案

### 5.1 推荐方案：统一Knowledge文档类型

不为六个栏目复制六套相似Contentlayer类型。新增一个`Knowledge`类型，通过`category`区分栏目，文件按目录组织：

```text
data/
├─ knowledge/
│  ├─ topics/
│  ├─ methods/
│  ├─ variables/
│  ├─ literature/
│  ├─ stata/
│  └─ writing/
├─ authors/
├─ servicesData.ts
└─ siteMetadata.js
```

建议字段：

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| title | string | 是 | 页面标题和H1 |
| summary | string | 是 | 搜索摘要、列表卡片、OG描述 |
| date | date | 是 | 首次发布日期 |
| lastmod | date | 是 | 最后核验日期 |
| category | enum | 是 | 六栏目之一 |
| subcategory | string | 否 | 二级筛选 |
| tags | string[] | 是 | 站内主题关系，不作为批量SEO页依据 |
| authors | string[] | 是 | 关联真实作者实体 |
| draft | boolean | 是 | 草稿不得进入列表、搜索和sitemap |
| canonicalUrl | string | 否 | 转载或迁移时使用 |
| difficulty | enum | 否 | 入门/进阶/高级 |
| stage | string[] | 否 | 选题/开题/实证/写作/答辩 |
| methods | string[] | 否 | 相关实证方法 |
| software | string[] | 否 | Stata/R/Python等 |
| dataSources | string[] | 否 | 数据来源提示 |
| references | string或结构化数据 | 否 | 事实与方法依据 |
| video | object | 否 | 视频URL、封面、时长、上传日期 |
| faq | object[] | 否 | 页面中实际展示的问题与答案 |
| noindex | boolean | 否 | 低价值、重复或风险页控制 |

计算字段：

- `slug`：相对栏目路径。
- `url`：`/${category}/${slug}/`。
- `readingTime`：预计阅读时间。
- `toc`：正文目录。
- `structuredData`：Article及必要实体引用。
- `relatedIds`：基于显式配置优先，标签仅作补充。

### 5.2 服务和作者数据

- 作者继续使用现有Authors类型，并补充`bio`、`expertise`、`sameAs`、`credentials`、`reviewPolicy`等字段；所有资历必须可核验。
- 第1—2周服务卡片使用`data/servicesData.ts`静态配置即可，至少包含选题诊断、实证方法、Stata代码、论文写作和论文润色优化的服务名称、适用阶段、交付物与咨询入口。
- 案例功能不列为P0。如本阶段确有真实、获授权案例，可新增`CaseStudy`类型；否则首页不展示虚假案例占位。

### 5.3 默认示例内容处理

- 上线前将默认英文博客和模板作者设为草稿、删除或从生产构建中排除。
- 不将同一篇文章同时保留在`/blog/slug`和新栏目URL中。
- 若迁移已有正式URL，设置单跳301重定向并更新canonical和内部链接。

## 6. 首页与栏目页实现策略

### 6.1 首页

首页使用服务器组件读取精选Knowledge内容；只有咨询表单、筛选和弹层使用客户端组件。首屏不加载视频播放器、聊天SDK或大二维码原图。

首页应输出可抓取文本：品牌定位、六栏目名称、论文润色优化、服务范围、作者简介、常见问题和联系方式说明。二维码图片延迟加载，但联系按钮和文字说明不得依赖JavaScript才出现。

### 6.2 栏目页

六个栏目页静态生成，构建时按`category`过滤Knowledge。每页包含唯一栏目简介、精选条目、分类导航、更新内容和相关栏目。

筛选原则：

- 默认页面可索引。
- 客户端筛选结果不生成大量参数URL。
- `?tag=`、`?difficulty=`等筛选参数设置canonical回栏目页，必要时noindex。
- 只有具备独立搜索价值和足够原创内容的专题才创建静态聚合页。

### 6.3 详情页

详情页统一包含：面包屑、H1、摘要、作者、发布日期、最后核验日、目录、正文、参考资料、相关内容、纠错入口和情境化咨询CTA。

代码页必须显示软件版本、依赖包、输入数据结构、代码、输出解释和失败条件。变量页必须显示定义、单位、来源、授权说明和核验日期。

## 8. 结构化数据规划

| 页面 | Schema类型 | 核心关系 |
|---|---|---|
| 首页 | WebSite + Person或Organization | publisher、sameAs、url、potentialAction按真实功能设置 |
| 作者页 | ProfilePage + Person | mainEntity、sameAs、knowsAbout |
| 内容详情 | Article | headline、description、author、datePublished、dateModified、mainEntityOfPage、image |
| 内页 | BreadcrumbList | 首页→栏目→详情 |
| 咨询与润色页 | Service | provider、areaServed、serviceType，描述真实的研究辅导与论文润色优化服务 |
| 视频详情 | VideoObject | name、description、thumbnailUrl、uploadDate、duration、embedUrl/contentUrl |
| FAQ区域 | FAQPage（谨慎） | 问答必须在页面真实可见且内容一致 |

质量规则：

- 评分、评价、学校、学位或获奖信息仅在真实、可核验且页面可见时输出。
- VideoObject仅用于页面中可实际播放的视频。
- JSON-LD与页面可见内容、真实服务和营销表述保持一致。
- 结构化数据以帮助搜索引擎理解页面实体为目标，富结果展示以搜索引擎实际判断为准。

所有JSON-LD在上线前使用Google Rich Results Test和Schema Markup Validator检查；百度侧以真实可见正文和基础信息规范为主。

## 9. Sitemap、robots与抓取

### 9.1 Sitemap

现有`app/sitemap.ts`保留并扩展，包含：

- 首页、六栏目页、作者、咨询、论文润色、服务说明、隐私和联系页。
- 所有非草稿、非noindex的Knowledge详情页。
- 正确绝对URL和真实`lastModified`。
- 为百度提供直接URL列表的XML或TXT sitemap，不使用百度当前不处理的索引型sitemap作为唯一提交文件。

不包含：搜索结果、参数页、草稿、测试页、重复标签页、API和预览URL。不要依赖`priority`或`changefreq`制造排名预期。

### 9.2 Robots

现有`app/robots.ts`保留并检查：

- 允许抓取正式公开内容及必要CSS/JS/图片。
- 阻止API、预览、内部管理路径和测试路径。
- 指向唯一正式sitemap。
- 不用robots.txt隐藏本应noindex的HTML页面；已被索引的页面使用meta noindex或正确状态码处理。

### 9.3 搜索引擎验证

- P0：百度搜索资源平台完成主体和站点验证，提交全量sitemap；新增或重要更新的优质页面调用普通收录API提交，并记录配额、响应和失败重试。
- P1：Bing Webmaster Tools完成验证和sitemap提交；360、搜狗通过公开检索、源站日志和可用站长入口监测抓取与收录。
- P2：Google Search Console完成DNS验证和sitemap提交，仅用于境外与留学生流量监测。
- 验证值通过环境变量或部署配置注入，不把私密token硬编码进仓库。
- 百度推送token只保存在部署环境变量中，构建日志和前端代码不得暴露。

## 10. 内容SEO和内部搜索

### 10.1 内容质量门禁

每篇内容发布必须通过：

- 标题与正文问题一致。
- 作者、日期、最后核验日完整。
- 关键结论有引用或明确标注为经验判断。
- 代码经过可复现验证，示例数据不含用户隐私。
- 图片、图表、视频与正文高度相关。
- 无关键词堆砌、拼接、伪原创和批量空页。
- 至少两个上下文相关内部链接。
- 咨询CTA不遮挡正文，不伪装成下载按钮。
- 页面展示真实发布时间、最后核验时间和作者信息，时间字段与sitemap `lastModified`保持一致。
- 正文优先使用中国大陆高校常用术语，并覆盖用户会直接搜索的问题表达。

国内关键词集群首期至少包括：本科毕业论文、硕士论文、开题报告、实证分析、Stata报错、DID平行趋势、固定效应、稳健性检验、内生性、变量定义、导师意见、盲审修改、预答辩、论文返修、中文摘要、论文润色和参考文献格式。每个页面只承接一个明确主问题，近义检索词在同页自然解释。

### 10.2 本地搜索索引

扩展当前`createSearchIndex`，把非草稿Knowledge纳入搜索；索引字段仅保留标题、摘要、栏目、标签、URL和必要正文摘要，避免完整正文造成前端文件过大。

搜索结果页不进入sitemap并设置noindex。中文搜索需要同时测试中文问题、国内论文阶段用语、英文缩写和命令名，例如“盲审修改”“平行趋势”“DID”“reghdfe”。

### 10.3 内部链接实现

优先使用内容frontmatter中的显式`related`或`relatedIds`，确保方法、变量、代码和写作页之间形成可控关系；标签自动推荐仅作为补充。

栏目卡片和面包屑使用真实`<a>`链接，避免只有点击脚本。每个详情页链接回栏目，每个栏目链接首批高价值内容。

## 11. 性能与中文访问体验

- 保持内容页静态生成和React Server Components优先。
- 首屏不加载第三方视频、评论和二维码大图；在进入视口后延迟加载。
- 图片使用Next Image，明确width/height，防止布局偏移。
- 二维码使用单独的小尺寸展示资源，点击后再加载高清图。
- 正文使用系统中文字体栈或本地托管字体，不依赖运行时访问境外字体服务。
- 控制客户端JavaScript；目录、正文、作者和链接必须服务端输出。
- 统计脚本采用异步加载，统计失败不能影响正文和表单。
- 首页和内容页不把YouTube、Google Fonts、Google Analytics、reCAPTCHA、Gravatar等境外服务放入核心请求链路。
- 在中国移动、中国联通、中国电信及可获得的校园网环境分别测试首屏、表单、二维码和视频跳转。
- 以国内手机网络为基准，P0页面首屏主体目标1.5秒内可见并向1秒优化，LCP目标不高于2.5秒；记录地区、运营商、设备和测试时间。
- 上线前使用国内测速节点和浏览器性能工具双重检测，分别记录DNS、TLS、TTFB、首屏、LCP和失败请求。

## 12. 二维码素材技术方案

### 12.1 源文件

- `doc/图片资料/微信二维码.jpg`：928×1380，121927字节。
- `doc/图片资料/QQ二维码.png`：1220×1478，412748字节。

2. 人工确认图片内容和账号归属。
3. 裁切二维码主体并保留二维码静区，不进行破坏识别的过度压缩。
4. 微信二维码优先转换为无损PNG。
5. 生成展示尺寸和高清弹层尺寸。
6. 使用ASCII文件名放入：

public/static/images/contact/wechat-qr.png

7. 使用微信和QQ真实App分别扫码测试桌面、手机截图和不同亮度。

## 13. 咨询表单技术方案

### 13.1 请求流程

```text
ConsultationForm
  → POST /api/consultation
  → 内容类型和请求大小检查
  → 服务端字段验证
  → 蜜罐/时间阈值/限流
  → 服务说明与隐私确认
  → 生成线索ID
  → 发送通知或写入已确认的数据存储
  → 返回通用成功信息
  → 记录consult_submit事件
```

### 13.2 字段与验证

建议字段：

- `discipline`：枚举或限定长度。
- `degreeStage`：本科/硕士/博士/教师/其他。
- `researchStage`：选题/开题/数据/实证/写作/答辩/返修。
- `problemSummary`：必填，限制长度，纯文本处理。
- `dataStatus`、`methodStatus`：可选，限制长度。
- `serviceType`：选题诊断/实证方法/Stata代码/论文写作/论文润色优化等服务枚举。
- `polishingFocus`：语言表达/结构逻辑/术语统一/图表表述/引用与格式/摘要标题关键词/返修说明，可多选。
- `wordCountRange`：润色文本预计字数范围。
- `documentStage`：初稿/修改稿/投稿稿/返修稿/答辩稿。
- `timeline`：可选。
- `contactType`与`contactValue`：二选一，格式和长度校验。
- `consent`：服务说明与隐私确认，必须为true。
- `sourcePath`、UTM字段：由前端提供但服务端按不可信输入处理。

首版通过文字摘要完成需求初筛；确认服务后，通过约定的安全方式交换必要材料。日志采用字段最小化和脱敏规则，不记录完整联系方式、论文正文、数据和表单原文。

### 13.3 安全和反垃圾

- 服务端验证，不能只依赖浏览器校验。
- 限制POST请求体大小和文本长度。
- HTML转义或只按纯文本处理，防止存储型XSS。
- IP或匿名标识限流，具体方案按部署平台选择。
- 蜜罐字段和最短填写时间阻挡简单机器人。
- 校验Origin/Referer作为辅助，不作为唯一安全措施。
- 错误响应不暴露堆栈、通知地址和内部服务信息。
- 密钥只存环境变量。
- 通知失败进入受控重试或错误监控，不能向用户显示敏感原因。
- 隐私政策说明用途、保存时间、访问和删除方式。

### 13.4 数据存储决策

第1—2周优先选择“通知可靠、存储最少”的方案：

- 方案A：服务端验证后发送到站点所有者确认的邮箱/工作流，同时只记录匿名事件；开发最快。
- 方案B：在已确认的数据库保存线索ID、时间、来源、状态和必要联系信息；适合需要跟进状态。
- 不建议直接把表单内容发送到公开群机器人或写入无权限控制的在线表格。

最终方案取决于部署平台、通知渠道和隐私主体，实施前必须确认。微信个人号和QQ个人号没有通用、安全的服务端收件API，不能假设可自动推送。

## 15. CSP、安全响应头与第三方服务

当前CSP允许`unsafe-inline`、`unsafe-eval`及较宽的`connect-src *`和`img-src *`。第1—2周先确保功能正确，随后按实际使用的Umami、视频、图片和表单域名收紧：

- 外部视频iframe只允许实际平台，并设置合理的sandbox/referrer策略。
- 表单接口只接受本站预期请求。
- 保留HSTS、nosniff、DENY frame等已有安全头，并测试是否影响真实嵌入需求。
- 移除不用的评论、newsletter或分析服务配置，减少第三方攻击面和隐私披露。

| 没有可复制账号 | 移动端联系困难 | 所有者手工提供并确认公开范围 |
| 通知渠道未定 | 表单可能无法闭环 | 确认邮箱/工作流/数据库方案 |
| 默认文章仍公开 | 稀释中文经管主题 | 上线前转草稿或删除 |
| 批量AI内容 | 低质、重复、事实和代码错误 | 建立人工审核门禁 |
| 润色范围与交付层级定义不清 | 用户预期和报价不一致 | 明确基础语言润色、深度结构润色、格式规范及复查次数 |
