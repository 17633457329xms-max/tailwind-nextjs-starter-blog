# 正式上线部署手册（个人站、国内 SEO 优先）

> 适用项目：`tailwind-nextjs-starter-blog`（谢老师讲论文 · 多学科研究辅导/润色一对一定制）
> 当前版本：2026-09-01 更新（对齐最新项目：12 学科多层级内容、Umami 已接入、Railway 预览环境、GitHub Actions 自动发布）
> 目标：以个人可承受的预算和维护精力，获得稳定的中国大陆访问体验、可持续收录与可回滚的上线流程。
> 定位：研究方法教学、选题诊断、写作反馈、论文润色优化一对一定制。公开页面不使用“代写、包过、保证毕业”等高风险表达。

---

## 1. 先给结论：采用这一套（唯一推荐，不做二选一）

**杭州（或任意大陆地域）阿里云轻量应用服务器 + 个人 ICP 备案 + Ubuntu 24.04 LTS + Node.js 20 LTS + Yarn + PM2 + Nginx + 免费 HTTPS + GitHub Actions 自动发布 + Umami(已在用) + 百度统计 + 百度/Bing 站长平台。**

- **唯一主站**：`https://你的主域名.com`（不带 `www`），部署在阿里云大陆轻量服务器。
- **预览/回退环境**：继续保留 `https://lw.up.railway.app`（Railway），只用于新功能预览和线上回退对照，**不参与正式收录**（详情见第 3.3 节）。
- **自动发布**：每次推送 GitHub `main`，服务器自动拉取、构建、重启，不再手动 SSH 执行命令。
- **统计**：继续使用已在运行的 `cloud.umami.is` + 补上百度统计（国内自然搜索数据以百度为准）。

为什么是这一套而不是更省事的选择：

| 候选 | 为什么不用 | 定位 |
| --- | --- | --- |
| 只用 Railway 子域名做正式站 | 境外免费子域名在百度收录权重极低、大陆访问不稳定、随时可能休眠，见第 13 章量化对比 | 只做预览 |
| Vercel / Cloudflare Pages 做正式主站 | 境外节点大陆访问不稳，无法备案，百度抓取差 | 不用 |
| 1 核 1 GB 便宜服务器 | Next.js 15 + contentlayer2 构建需要内存余量，1 核 1 GB 构建会 OOM | 不用 |
| 一开始就上 Docker / K8s / 多台服务器 | 单人维护负担过大，初期无此必要 | 不用 |
| 百度统计与 Umami 只留一个 | 一个管国内自然搜索（百度），一个管匿名埋点（Umami），作用不同，两个都要 | 组合使用 |

### 1.1 推荐配置与预算边界（每项唯一推荐）

| 项目 | 唯一推荐 | 原因 |
| --- | --- | --- |
| 服务器 | **阿里云轻量应用服务器，中国大陆地域**（推荐杭州），**2 核 4 GB、60 GB SSD、5 Mbps** | 域名、备案、服务器、SSL、CDN 一个控制台；2 核 4 GB 保证构建不 OOM |
| 系统 | **Ubuntu 24.04 LTS** | 文档多、与项目 Node 20 兼容好 |
| 域名 | **1 个主 `.com`，不带 `www`**（推荐 `xueshuyanjiu.com` 等，见 2.1） | 短、好口播、好印二维码 |
| DNS | **阿里云 DNS** | 与服务器备案一个账户，排查最省事 |
| HTTPS | **Certbot 免费证书**（自动续期） | 零成本、自动 |
| CDN | **首月不开**；月访问稳定超过 1 万且页面明显变慢时，再开阿里云 CDN | 初期内容和收录优先 |
| 图床 | **首月不上图床**；图片量大再评估阿里云 OSS+CDN | 当前文章配图量在服务器带宽承受内 |
| 自动发布 | **GitHub Actions**（新增，见第 6 章） | 消除手动 SSH 部署 |
| 统计 | **Umami(cloud) + 百度统计** | 见上文 |
| 提交收录 | **百度主动推送脚本 `scripts/submit-baidu.mjs`** + 站长平台手动提交 sitemap | 项目已内置脚本 |

### 1.2 购买入口与固定选择（逐步操作）

1. **购买服务器**：打开 [阿里云轻量应用服务器](https://www.aliyun.com/product/swas)，选**中国大陆地域（杭州）、Ubuntu 24.04、2 核 4 GB、60 GB SSD、5 Mbps**。下单前确认该实例支持 ICP 备案（新用户首年常有折扣，续费通常更高，以购物车为准）。
2. **购买域名**：打开 [阿里云域名注册](https://wanwang.aliyun.com/domain)，先搜索候选域名，显示可注册再付款；域名实名用与备案相同的本人信息。
3. **办理备案**：打开 [阿里云 ICP 备案](https://beian.aliyun.com/)，选“首次备案 / 个人”，按页面完成人脸核验、网站信息、域名核验、短信核验。备案规则会变动，以下单日控制台要求为准。
4. **搜索收录**：正式域名可访问后，依次验证 [百度搜索资源平台](https://ziyuan.baidu.com/)、[百度统计](https://tongji.baidu.com/)、[Bing Webmaster Tools](https://www.bing.com/webmasters/)，提交 `https://主域名/sitemap.xml`。

## 2. 上线前必须完成的决策

### 2.1 主域名与 URL 规则（唯一推荐）

1. **主域名：一个不带 `www` 的 `.com`**，即 `https://你的主域名.com`。
2. **`www` 版本与 HTTP 版本永久 301** 跳转到 `https://你的主域名.com`。
3. **文章 URL 一经上线不改**；改标题可以，改 slug 必须做 301。
4. 域名与服务器备案主体统一用本人真实信息。

### 2.2 域名风险与五个候选（逐个明确）

**不要用 `lunwendaixie.com`。** 域名本身不必然违规，但直接含“论文代写”会带来三类现实风险：备案/广告/平台审核要求说明业务；被用户和平台理解为代写站，损害“研究辅导、润色优化”品牌；关键词域名不是国内排名捷径，反而风险大于收益。

**唯一候选顺序**（必须在阿里云域名搜索页实时确认可注册，拼音短、含义正面、可覆盖多学科、适合口播与微信名片）：

| 优先级 | 候选 `.com` | 推荐原因 |
| ---: | --- | --- |
| 1 | `xueshuyanjiu.com` | 覆盖研究方法、选题和多学科，品牌边界最稳 |
| 2 | `yanjiufangfa.com` | 与“研究方法、实证分析、文献综述”高意图内容直接相关 |
| 3 | `xuelunzhinan.com` | 易记，适合教程、视频和知识库 |
| 4 | `lunwenfangfa.com` | 明确覆盖论文方法，不触及代写 |
| 5 | `yanjiuxiezuo.com` | 适合写作、文献与润色优化内容集群 |

**只注册并运营一个主域名。** 预算允许时，再注册同名 `.cn` 仅做品牌保护并 301 到 `.com`，不要做成两个可收录网站。

### 2.3 经济成本与年度预算（唯一推荐，口径对齐最新项目）

个人站的保守可执行预算区间，不是固定报价；促销、续费、地域会变化，下单前以阿里云购物车为准。

| 项目 | 首年预估 | 次年预估 | 是否必须 | 说明 |
| --- | ---: | ---: | ---: | --- |
| `.com` 域名 | ¥55–90 | ¥65–95 | 必须 | 只买一个主域名 |
| 阿里云轻量服务器 2 核 4 GB（大陆） | ¥200–500 | ¥400–800 | 必须 | 首年常有折扣，续费通常更高 |
| ICP 备案 | ¥0 | ¥0 | 必须 | 服务商备案服务通常免费 |
| 免费 SSL 证书 | ¥0 | ¥0 | 必须 | Certbot 自动续期 |
| Umami（cloud.umami.is） | ¥0 | ¥0 | 已在用 | 免费额度内 |
| 百度统计、百度/Bing 站长平台 | ¥0 | ¥0 | 建议 | 前期足够 |
| 备份（本地加密盘或低量对象存储） | ¥0–60 | ¥0–120 | 建议 | 先备份代码、`.env.local`、Nginx 配置 |
| 阿里云 CDN | ¥0 | ¥0–300 | 后置可选 | 首月不开，达到性能瓶颈再开 |
| GitHub Actions（本项目用量） | ¥0 | ¥0 | 免费 | 个人仓库免费额度足够 |
| **合计（不启用 CDN）** | **¥255–650** | **¥465–1,015** |  | 一人可控制的基础成本 |

**不预购**：SEO 外链包、采集工具、海外加速、独立数据库、付费监控、多台服务器。内容生产和持续更新的时间成本远高于基础云资源成本。

### 2.4 自然流量与微信、QQ 私域转化预测（口径对齐最新 12 学科内容）

预测以当前 12 个一级学科、数百篇分层文章为起点。假设：每周新增或实质更新 2–4 篇；每周发布 1 个长视频并拆短内容；每篇视频和站外内容都链接到对应站内文章；不买刷量或垃圾外链。搜索收录通常有 4–12 周滞后，以下为**区间预测而非承诺**。

| 上线阶段 | 月自然搜索访问 | 微信新增联系 | QQ 新增联系 | 有效咨询（合计） | 判断依据 |
| --- | ---: | ---: | ---: | ---: | --- |
| 第 1 月 | 0–300 | 0–4 | 0–1 | 0–3 | 备案刚提交收录，主要依赖视频和熟人入口 |
| 第 3 月 | 400–1,500 | 4–22 | 1–8 | 3–20 | 部分长尾词开始收录，学科内容形成内链 |
| 第 6 月 | 2,000–6,000 | 20–85 | 6–30 | 12–70 | 有持续更新、视频导流和文章集群的前提下 |
| 第 12 月 | 6,000–18,000 | 60–260 | 20–90 | 45–220 | 需已有稳定收录、品牌搜索与高质量更新 |

估算漏斗：自然访问 → 联系入口点击约 **0.8%–2.5%**；点击 → 成功添加微信/QQ 约 **35%–65%**；成功添加 → 有效咨询约 **40%–65%**。微信预计占新增私域联系的 **70%–80%**，QQ 占 **20%–30%**。若更新停止、质量下降或站点不稳定，结果可能低于区间；这不是收入承诺。

> 相对纯 Railway 子域名站的提升量化见 **第 13 章**。核心结论：正式域名 + 大陆 IP 是“从基本不被百度收录 → 能被收录并参与排名”的质变，其余是速度与信任的增益。

## 3. Railway 与正式站的协同

### 3.1 Railway 保留为预览环境

`https://lw.up.railway.app` 继续保留，用途：

1. **新功能预览**：正式站上线后，每次改动先在本地验证，再推 main 触发正式站自动部署；若想先看效果再上正式站，可临时推预览分支让 Railway 构建（Railway 监听 GitHub 自动部署）。
2. **线上回退对照**：正式站出问题时，可先用 Railway 检查是否为代码问题。

### 3.2 不要把 Railway 子域名做正式收录

- Railway 子域名属于境外免费域名，百度等国内引擎对它的收录权重极低、抓取不稳定。
- **不要让 Railway 子域名与正式域名同时被收录**：正式域名上线后，不要做 `lw.up.railway.app` → 正式域的 301（会永久转移权重但也会在迁移期产生抓取抖动），也不要在 Railway 上继续发布面向正式收录的内容；把它当内部预览工具即可。

### 3.3 正式域名上线后的迁移动作（逐步）

1. 在 `data/siteMetadata.js` 把 `defaultSiteUrl` 的 `https://lw.up.railway.app` 改为正式 HTTPS 域名（或靠服务器 `.env.local` 的 `NEXT_PUBLIC_SITE_URL` 覆盖，推荐用环境变量，见 4.3）。
2. 在 Railway 控制台把部署暂停或设为手动，避免它继续构建抢占/混淆。
3. 在服务器 `.env.local` 写入正式站环境变量后重新构建（见第 4、6 章）。
4. 用无痕窗口访问正式域名，检查：页面、sitemap、robots、咨询页、微信/QQ 复制、Umami 上报全部正常。
5. 再到百度/必应站长平台提交 sitemap。

## 4. 服务器首次配置

以下命令在服务器 SSH 终端执行。`YOUR_USER`、`YOUR_DOMAIN`、`YOUR_REPO` 替换为实际值。

### 4.1 登录并创建普通部署用户

```bash
ssh root@服务器公网IP
apt update && apt upgrade -y
adduser deploy
usermod -aG sudo deploy
su - deploy
```

日常部署用 `deploy` 用户，不长期用 root。云防火墙只放行 `80`、`443` 和个人固定 IP 的 `22` 端口。

### 4.2 安装基础软件、Node 与 Yarn

```bash
sudo apt install -y git nginx curl build-essential
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs
corepack enable
corepack prepare yarn@3.6.1 --activate
node -v
yarn -v
```

项目 `package.json` 已声明 `yarn@3.6.1`，部署用 Yarn，不要混用 npm。

### 4.3 拉取项目并配置环境变量

```bash
sudo mkdir -p /var/www/paper-site
sudo chown -R deploy:deploy /var/www/paper-site
cd /var/www/paper-site
git clone YOUR_REPO .
cp .env.example .env.local   # 若仓库没有该文件则新建
nano .env.local
```

`.env.local` 至少配置（名称以项目实际为准）：

```bash
NEXT_PUBLIC_SITE_URL=https://YOUR_DOMAIN
NEXT_UMAMI_ID=你的umami_website_id
NEXT_PUBLIC_UMAMI_SRC=https://cloud.umami.is/script.js
BAIDU_SITE=YOUR_DOMAIN
BAIDU_PUSH_TOKEN=你的百度推送token
```

> **注意**：`NEXT_PUBLIC_SITE_URL` 必须在**构建时**生效，因为它会被编译进 sitemap/robots/canonical/JSON-LD。改它后必须重新 `yarn build`（自动发布 workflow 每次都全新构建，天然满足）。

不要把 API 密钥、统计 token、微信/QQ 私密信息提交到 Git。`.env.local` 只保存在服务器和个人加密备份中。

### 4.4 首次构建与启动

```bash
cd /var/www/paper-site
yarn install --immutable
yarn typecheck
yarn lint
yarn build
yarn serve
```

确认本机 `http://127.0.0.1:3000` 能访问后，`Ctrl + C` 停止，交给 PM2 常驻。

## 6. GitHub Actions 自动发布（新增，消除手动 SSH 部署）

### 6.1 原理

本地（或任何电脑）推送 `main` → GitHub 触发 `deploy.yml` → workflow 用 SSH 连上服务器 → 服务器执行 `git pull && yarn install && yarn build && pm2 reload`。你**不需要**再手动登录服务器执行第 9 节的命令。

### 6.2 一次性准备（在服务器执行一次）

1. 在服务器 `deploy` 用户下生成部署密钥并配置 GitHub 免密拉取：

```bash
su - deploy
cd /var/www/paper-site
git remote set-url origin https://github.com/YOUR_USER/YOUR_REPO.git
# 配置部署密钥（让服务器可以免密 clone/pull 私有或公开仓库）
```

**推荐用 Deploy Key**（只读仓库，最安全）：
- 在服务器生成 SSH 密钥：`ssh-keygen -t ed25519 -C "deploy@server" -f ~/.ssh/deploy_key`
- 在 GitHub 仓库 `Settings → Deploy keys → Add` 粘贴公钥，勾选 **Allow write access**（如果后续 workflow 需要 push 才勾，否则保持只读）。
- 在服务器 `~/.ssh/config` 添加：

```text
Host github
  HostName github.com
  User git
  IdentityFile ~/.ssh/deploy_key
```

### 6.3 配置 SSH 免密从 GitHub Actions 连到服务器

在 GitHub 仓库 `Settings → Secrets and variables → Actions → New repository secret` 添加以下 Secret：

| Secret 名 | 内容 |
| --- | --- |
| `SERVER_HOST` | 服务器公网 IP |
| `SERVER_USER` | `deploy` |
| `SERVER_SSH_KEY` | 服务器上 **Actions 专用**私钥（`ssh-keygen` 生成一对新密钥，公钥追加到服务器 `~/.ssh/authorized_keys`，私钥填到这里） |
| `SERVER_PATH` | `/var/www/paper-site` |

> 不要把服务器主登录密钥当 Actions 密钥；用一对独立密钥，方便随时吊销。

### 6.4 新增 `.github/workflows/deploy.yml`

在仓库根目录新建 `.github/workflows/deploy.yml`（推送到 `main` 即触发）：

```yaml
name: Deploy to Production

on:
  push:
    branches: [main]

concurrency:
  group: production
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: SSH Deploy
        uses: appleboy/ssh-action@v1.2.0
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            set -e
            cd ${{ secrets.SERVER_PATH }}
            git fetch --all --prune
            git reset --hard origin/main
            yarn install --immutable
            yarn build
            pm2 reload paper-site --update-env
            curl -sf -I https://YOUR_DOMAIN/sitemap.xml > /dev/null && echo "deploy ok"
```

> `yarn build` 内的 `next build` 会生成 sitemap（由 `app/sitemap.ts` 在构建时生成）与 RSS（由 `scripts/postbuild.mjs` 生成）。若 `yarn build` 后需要额外执行 `yarn submit:baidu`（主动推送新 URL 给百度），可在此 workflow 中追加一步（见 6.5）。

### 6.5 百度主动推送并入自动发布（可选但推荐）

在 `deploy.yml` 的 `script` 末尾追加（需要服务器 `.env.local` 已配置 `BAIDU_SITE` 和 `BAIDU_PUSH_TOKEN`）：

```bash
cd ${{ secrets.SERVER_PATH }}
set -a; source .env.local; set +a
yarn submit:baidu || echo "百度推送失败（不影响站点）"
```

这样每次发布后，新文章 URL 自动推给百度，省去手动提交。

### 6.6 验证自动发布

推送一次 `main`，在 GitHub 仓库 `Actions` 页确认 workflow 变绿；随后访问正式站确认新代码已生效。后续日常更新 = **本地改 → 本地验证 → push main → 结束**，无需再碰服务器。

## 7. Nginx 与 HTTPS 配置

### 7.1 Nginx 反向代理

创建 `/etc/nginx/sites-available/paper-site`：

```nginx
server {
    listen 80;
    server_name YOUR_DOMAIN www.YOUR_DOMAIN;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

启用并检查：

```bash
sudo ln -s /etc/nginx/sites-available/paper-site /etc/nginx/sites-enabled/paper-site
sudo nginx -t
sudo systemctl reload nginx
```

DNS 中把主域名和 `www` 的 A 记录指向服务器公网 IP，生效后再申请证书。

### 7.2 免费 HTTPS 与强制跳转

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d YOUR_DOMAIN -d www.YOUR_DOMAIN
sudo certbot renew --dry-run
```

Certbot 会协助配置 HTTPS 跳转。随后让 `www.YOUR_DOMAIN` 301 到 `https://YOUR_DOMAIN`（在 Nginx 的 server 块里加 return，或用 certbot 生成的配置调整），避免两个版本同时被收录。检查：

```bash
curl -I http://YOUR_DOMAIN
curl -I https://YOUR_DOMAIN
curl -I https://YOUR_DOMAIN/sitemap.xml
curl -I https://YOUR_DOMAIN/robots.txt
```

要求：HTTP 自动跳 HTTPS；非主域名跳主域名；`sitemap.xml` 与 `robots.txt` 返回 `200`。

## 8. 国内 SEO 上线清单（最重要）

### 8.1 必做技术项

- [ ] `NEXT_PUBLIC_SITE_URL` 改为正式 HTTPS 主域名后重新构建（推荐在服务器 `.env.local` 中设置，见 4.3；不要直接改 `data/siteMetadata.js` 里的默认值）。
- [ ] 首页、12 个学科页、各专业/文章页均可返回 `200`，无登录墙、验证码墙或地区拦截。
- [ ] `https://主域名/sitemap.xml` 包含全部学科与文章 URL（项目 `app/sitemap.ts` 已生成，覆盖静态页 + 知识库 + 学科 + 专业 + 文章）。
- [ ] `https://主域名/robots.txt` 不屏蔽公开页面、学科页、sitemap（`app/robots.ts` 已处理，只 disallow `/api/` 和 webpack-hmr）。
- [ ] 每篇文章有唯一 `<title>`、meta description、canonical、发布日期/更新时间和 Article 结构化数据（`siteMetadata` + 各页面 generateMetadata 已实现）。
- [ ] 文章之间至少有 2–4 个语义相关内链。
- [ ] 移动端首屏可读、图片压缩、无大体积自动播放视频。
- [ ] 404 页返回真正的 404；过期文章做 301，不要全部跳首页。

### 8.2 国内站长平台动作

1. 注册并验证 **百度搜索资源平台**（ziyuan.baidu.com），验证整个主域名。
2. 提交正式 sitemap URL；新文章发布后由自动发布 workflow 里的 `yarn submit:baidu` 主动推送，另可在后台手动提交一次全量。
3. 注册 **Bing Webmaster Tools**，提交同一个 sitemap。
4. 360、搜狗、微信搜一搜以自然发现和站外内容入口为主；站长入口可用再验证提交，不要为提交动作反复改站结构。
5. 任何平台抓取异常，先查 `robots.txt`、HTTP 状态码、canonical、服务器日志和页面是否可被未登录访客访问。

### 8.3 内容策略：比“堆 SEO 词”更有效

每篇文章只解决一个明确问题，标题覆盖学生自然搜索表达：

- “教育学论文访谈怎么做：访谈提纲、样本与编码分析”
- “法学论文案例分析怎么写：事实、争点与裁判理由”
- “Stata 固定效应模型怎么选：个体、时间与双向固定效应”
- “文学论文文本细读怎么写：引文证据与理论解释”

建议每周只新增 **2–4 篇**真正有深度的文章，并同步录制 1 个长视频、拆出短视频，视频简介链接到对应文章页，不要全部导向首页。稳定更新六个月比一次性发布大量近似内容更有利于收录和信任。

## 9. 统计、转化与隐私

### 9.1 统计方案（唯一推荐：Umami + 百度统计）

1. **Umami**：已在用 `cloud.umami.is`，`.env.local` 配置 `NEXT_UMAMI_ID` 和 `NEXT_PUBLIC_UMAMI_SRC=https://cloud.umami.is/script.js`。`next.config.js` 的 CSP 已放行 `cloud.umami.is` 与 `gateway.umami.is`（含 `/api/send` 上报端点）。看匿名埋点：文章阅读、学科切换、二维码查看、微信号/QQ 复制、咨询按钮点击。
2. **百度统计**：补一个，重点看**国内自然搜索**来源、搜索词、落地页、地区、移动端比例。这一步对国内 SEO 判断至关重要，Umami 无法替代百度搜索词数据。
3. 只跟踪匿名事件，**不把**微信号、QQ 号、邮箱、论文标题、全文、附件内容传入任何统计系统。

### 9.2 每周只看四个指标

| 指标 | 用途 | 行动 |
| --- | --- | --- |
| 百度自然搜索点击 | 判断收录与排名是否增长 | 找增长最快的主题继续扩展 |
| 自然搜索落地页 | 判断用户真正搜索什么 | 给高流量文章补内链与明确咨询入口 |
| 文章阅读/停留 | 判断内容是否解决问题 | 优化开头、目录、表格和案例 |
| 咨询按钮/微信复制 | 判断转化 | 调整 CTA，不急于增加表单字段 |

## 10. 日常更新、发布与回滚

### 10.1 日常发布（配合 GitHub Actions，已自动化）

配置第 6 章后，日常发布 = **本地改 → 本地验证 → `git push origin main` → 结束**。GitHub Actions 会自动部署到服务器。

若暂时不想配置 Actions，仍可手动在服务器执行：

```bash
cd /var/www/paper-site
git pull --ff-only
yarn install --immutable
yarn typecheck && yarn lint && yarn build
pm2 reload paper-site --update-env
curl -I https://YOUR_DOMAIN/sitemap.xml
```

发布后抽查首页、一个学科页、一篇新文章、咨询页和手机端；再向百度提交新增文章 URL。

### 10.2 出问题时的回滚

```bash
cd /var/www/paper-site
git log --oneline -5
git checkout <上一个已验证提交>
yarn install --immutable
yarn build
pm2 reload paper-site --update-env
```

确认恢复后，再在本地修复问题。不要在服务器上直接改业务代码；服务器只用于部署。回滚后，把 `main` 恢复到上一个已提交版本并重新 push（若用自动发布，避免下一次 push 覆盖回滚）。

## 13. 正式站 vs Railway 个人站：提升量化对比

这是你问的核心问题。结论：**从 Railway 子域名迁到“阿里云大陆 + 备案独立域名”不是“优化提升”，而是“从基本不可被国内收录，到具备收录与排名资格”的质变**，其余是速度、信任和可控性的增益。分维度量化：

| 维度 | Railway 子域名 `lw.up.railway.app` | 阿里云大陆 + 备案独立域名 | 提升幅度 |
| --- | --- | --- | --- |
| **百度收录资格** | 境外免费子域名，百度收录权重极低，多数页面长期不被收录；无法用百度主动推送（token 需与域名绑定） | 大陆备案域名可主动提交收录、使用百度推送 API，sitemap 被正常抓取 | **质变：从“几乎不被收录”到“可收录可推送”** |
| **大陆访问速度（TTFB）** | 境外节点，跨境链路 300ms–2s 波动，高峰期更慢 | 大陆轻量节点，同城直连 50–150ms | **约 4–10 倍提速** |
| **访问稳定性** | 免费套餐有配额/休眠风险，偶发构建失败 | 自建常驻，可控 | 稳定可用性提升 |
| **品牌信任** | `railway.app` 子域名，陌生、不专业 | 简短独立 `.com`，可口播、可印二维码，信任度高 | 转化与口碑增益 |
| **SEO 长期权重** | 子域名权重随 Railway 域名走，无法积累品牌词 | 独立域名权重可积累品牌词、沉淀外链 | 长期资产增益 |
| **内容分发** | B站/知乎/视频号简介放 railway.app 子域名，观感差、点击率低 | 独立域名，适合全平台导流沉淀 | 站外引流转化增益 |
| **成本** | ¥0（但有限额/休眠） | 首年 ¥255–650，次年 ¥465–1,015 | 可控的确定性投入 |
| **可维护性** | 依赖第三方平台规则 | 自建 + GitHub Actions 自动发布，脚本化 | 可控性更高 |
| **预期月自然搜索（第 3–6 月）** | 接近 0（未被收录） | 400–6,000（见 2.4 区间） | 从无到有 |

### 不可承诺、也不该被承诺的部分

- 独立域名 + 大陆 IP **不保证**一定排到百度首页；排名取决于内容质量、收录稳定性、用户行为、内链与站外导流。
- “提升多少倍”不能只看基建。**内容持续更新 + 视频/站外导流到具体文章页**，才是流量曲线是否走高的真正变量。
- Railway 子域名并不是“浪费”：它作为预览/回退环境很有价值，见第 3 章。

**一句话**：正式站相对 Railway 个人站，**基础设施层面提升是“质的”——可收录、可推送、可稳定访问、可积累品牌；但能不能把流量做起来，取决于你能否维持每周 2–4 篇高质量内容 + 站外导流，而不是取决于服务器本身。**

## 14. 发布前仍需完成的项目优化与 Git 策略

### 14.1 上线前必须补齐的优化

以下比继续增加服务器配置更重要，应在正式提交百度收录前完成：

| 优先级 | 优化项 | 原因与验收方式 |
| ---: | --- | --- |
| P0 | 将 `siteMetadata.siteUrl` / `NEXT_PUBLIC_SITE_URL` 改为正式不带 `www` 的 HTTPS 域名 | 构建后检查所有 canonical、sitemap、JSON-LD 不再出现 `localhost` 或 `lw.up.railway.app` |
| P0 | 跑一次 `scripts/submit-baidu.mjs`（用正式域名和 token）核对 URL 数量 | 确认主动推送脚本覆盖全部文章 URL |
| P0 | 确认咨询入口只记录匿名事件（微信/QQ 复制、二维码查看、咨询页访问），无联系数据落库 | `app/api/consultation` 目录当前为空，符合预期；继续确保不引入表单落库 |
| P1 | 压缩二维码与文章配图，使用 WebP/AVIF | 保持移动网络首屏快；图片保留描述性 alt 文本 |
| P1 | 为每篇文章补 2–4 个相关推荐链接 | 形成学科主题集群，让爬虫和读者继续阅读 |
| P1 | 增加真实的作者页、更新政策与内容校验说明 | 提升专业信任；不虚构学历、案例或服务成果 |
| P2 | 当日均访问稳定超过 1,000 再评估 CDN、图床 | 数据与性能达到阈值后再加维护负担 |

### 14.2 Git 发布分支策略（唯一推荐）

**不长期维护“生产分支”。** 用短生命周期的发布标签：

```text
main（持续开发、已通过本地测试）
  └── 打标签 v1.0.0（服务器只部署这个已验证标签）
```

```bash
git switch main
git pull --ff-only
git tag -a v1.0.0 -m "first production release"
git push origin main --tags
```

服务器首次上线检出标签而不是“最新 main”：

```bash
cd /var/www/paper-site
git fetch --tags
git checkout v1.0.0
yarn install --immutable && yarn build
pm2 reload paper-site --update-env
```

> 注意：若启用了第 6 章 GitHub Actions 自动发布，默认监听 `main` 分支推送；打标签不会触发 deploy.yml（除非额外配置 tag 触发）。首次上线可先手动检标签部署，日常更新走 `main` 自动发布即可。需要精确回滚时用 10.2。
